# Specification of the tools exposed to the agent

Contract between the model and the middleware. Each tool is declared through function calling on the AI gateway. No write tool exists: the list below is exhaustive and closed.

Structural exception: `get_iocs_for_campaign` (section 1) is **not** declared to the model. It is the only flow leaving the perimeter, and it is confined to the upstream phase: it lives in a separate registry, invocable only through the analyst endpoint `/enrich`, before indicator validation. During the investigation loop, the agent materially has no tool whose flow leaves the internal perimeter — a string read from a SIEM result can therefore never become an outbound request, even on a successful prompt injection.

## Common principles

- Strict schema validation on input. Any non-conforming query is rejected before execution, with no call to the SIEM.
- Each tool applies its caps on the middleware side. The model cannot exceed them, even if it asks to.
- Each response indicates whether the result was truncated, so the model knows it is not seeing everything and refines its query rather than wrongly concluding.
- Each SIEM query leaves a trace for the analyst: its objective (`intent`), the columns and a sample of at most ten rows, already minimized by the middleware then rehydrated locally. This sample feeds the live hunt feed and the report appendix; the model never sees the rehydrated version. The version actually transmitted to the model (pseudonyms in place, free text masked where applicable) is kept alongside, with a count of pseudonyms by family and the state of the semantic pass: this is the visible proof of anonymization, query by query.
- Any error surfaces to the model in structured form (code, short message), never as a technical trace containing infrastructure elements.
- No secret, no technical identifier, no internal endpoint appears in the responses transmitted to the model.

## 1. get_iocs_for_campaign

Looks up the IOCs associated with a campaign or an actor against the whitelisted threat intelligence sources. The only tool whose flow leaves the internal perimeter — and for that reason, never exposed to the model: it is invocable only by the analyst through `/enrich`, in the upstream phase (statuses `draft` and `awaiting_ioc_validation` only).

Parameters:

| Name | Type | Required | Description |
|---|---|---|---|
| `campaign_name` | string | yes | Campaign, actor or TTP name. No internal context allowed. |
| `ioc_types` | array[string] | no | Filter: `hash`, `ip`, `domain`, `url`, `email`, `file_path`, `registry_key`. |
| `max_results` | integer | no | Default 50, cap 200. |

Response: a list of objects `{value, type, source_name, source_url, first_seen, confidence}`. Any IOC without a usable `source_url` is discarded by the middleware.

Guardrails:

- Domain whitelist applied at the network level, not just in the code.
- Anti-leak filter on the outbound request: only `campaign_name` and the IOC types leave. The middleware rejects the call if the string contains an internal pattern (hostname, private IP range, hunt identifier, staff name).
- No IOC generated by the model is accepted in return: the response comes exclusively from the queried source.
- The returned IOCs are marked `pending_validation` and cannot feed a SIEM tool until the analyst has validated them.

Implemented sources: VirusTotal, AlienVault OTX, ThreatFox and the CIRCL MISP OSINT feed (API and structured feeds — the latter is the only keyless one), plus the "vendor reports" source: search restricted to approved publishers (`SHL_TI_PUBLISHER_DOMAINS`), pages fetched from a whitelist, IOCs extracted by the model over untrusted wrapped content then re-validated by pattern on the code side (hexadecimal fingerprint, public IP, plausible domain). Each IOC cites the report page it comes from; a candidate invented by the model without a source page cannot exist.

## 2. run_secops_query

Runs a UDM search on Google SecOps, read-only.

| Name | Type | Required | Description |
|---|---|---|---|
| `udm_query` | string | yes | UDM query. |
| `intent` | string | yes | What the query is looking for, in one sentence. Shown to the analyst next to the result, in the hunt feed and in the report. |
| `start_time` | string (ISO 8601) | yes | Window start. |
| `end_time` | string (ISO 8601) | yes | Window end. |
| `max_rows` | integer | no | Default and cap 500. Up to 500 rows, the model receives everything and analyzes row by row; cap reached, it receives only aggregates and must refine. |
| `fields` | array[string] | no | Desired fields. Failing that, the middleware's default projection. |

Guardrails: identity = dedicated service account with the Chronicle API Viewer role (no write access to rules or feeds). Maximum window bounded by the tenant's retention. Query rejected if it contains any operation other than a search.

## 3. run_sentinel_kql

Runs a KQL query on the Log Analytics workspaces hosting Sentinel.

| Name | Type | Required | Description |
|---|---|---|---|
| `kql_query` | string | yes | Read-only KQL query. |
| `intent` | string | yes | What the query is looking for, in one sentence. Shown to the analyst next to the result, in the hunt feed and in the report. |
| `workspace` | string | yes | Logical workspace identifier, resolved on the middleware side. |
| `timespan_days` | integer | no | Default 7, cap 30 (extensible on analyst validation). |
| `max_rows` | integer | no | Default and cap 500. |

Guardrails: identity = Entra ID app registration with the Log Analytics Data.Read permission and the Log Analytics Reader role assigned per workspace. The middleware systematically injects a safety `| take N`. Write or mutation operators are rejected by query analysis before sending. The real workspace name is never exposed to the model.

## 4. run_defender_hunting

Runs an Advanced Hunting query on Microsoft Defender through the Graph security API.

| Name | Type | Required | Description |
|---|---|---|---|
| `kql_query` | string | yes | Advanced Hunting KQL query. |
| `intent` | string | yes | What the query is looking for, in one sentence. Shown to the analyst next to the result, in the hunt feed and in the report. |
| `timespan_days` | integer | no | Cap 30 (limit imposed by the API). Failing that, the depth is the one carried by the query's time filter, bounded to 30 days and to the investigation period. |
| `max_rows` | integer | no | Default and cap 500 on the middleware side. |

Guardrails: identity = Entra ID app registration with the application permission `ThreatHunting.Read.All` (admin consent required), endpoint `POST /security/runHuntingQuery`. Do not use the older Defender XDR API. Structural limits to respect: 30 days of maximum depth, 100,000 rows on the API side, quotas of 45 calls per minute and 1,500 per hour. The middleware applies its own cap of 500 rows, far below the API limit, for minimization.

## 5. record_finding

Records a finding in the current investigation file. Internal write only, no effect on the SIEMs.

| Name | Type | Required | Description |
|---|---|---|---|
| `title` | string | yes | Short title of the finding. |
| `description` | string | yes | Explanation and reasoning. |
| `severity` | string | yes | `info`, `low`, `medium`, `high`, `critical`. |
| `confidence` | string | yes | `low`, `medium`, `high`. |
| `entities` | array[object] | no | Entities concerned (`{type, value}`). |
| `evidence_query_ids` | array[string] | yes | Identifiers of the queries that produced the evidence. |

Guardrail: a finding without `evidence_query_ids` is refused. Every finding must be attachable to a query actually executed, which makes the report verifiable and prevents unsupported conclusions.

## 6. conclude_hunt

Closes the investigation and triggers report generation.

| Name | Type | Required | Description |
|---|---|---|---|
| `verdict` | string | yes | `benign`, `suspicious`, `escalate`, `inconclusive`. |
| `summary` | string | yes | Investigation summary. |
| `timeline` | array[object] | no | Ordered events (`{timestamp, event, source}`). |
| `limitations` | string | yes | What the hunt could not cover (retention, absent sources, truncations). |
| `attack_description` | string | no | Presentation of the searched-for attack for a reader who did not follow the hunt (modus operandi, objective, detection difficulty). Opens the report. |
| `techniques` | array[object] | no | Targeted MITRE ATT&CK techniques (`{id, name, description}`, 8 at most). The identifier must have the form `T1234` or `T1234.001`, otherwise the call is rejected. |
| `recommendation` | string | no | Proposed follow-up for the analyst (manual review, monitoring, no action). A proposal, never an executed action. |

Guardrails: the `limitations` field is mandatory, so the report always exposes its blind spots. The verdict is a proposal, not a decision: it goes to analyst review. The hunt scope shown at the top of the report (period, sources, budgets) is computed by the platform from the hunt's real parameters, never supplied by the model.

## Per-hunt budgets

The iteration and query budgets are proposed by the agent's playbook (an estimate computed by the code from the leads) and validated or adjusted by the analyst before launch; a launch without a validated playbook must set them explicitly. Absolute platform cap: 100 for each.

| Budget | Starting value |
|---|---|
| Iterations (tool calls) | playbook estimate (server default 20) |
| SIEM queries | playbook estimate (server default 15) |
| Tokens | cap defined with the platform team, alert at 80% |
| Duration | 15 minutes |

Overflow: clean stop, generation of a partial report flagging the interruption. Never a silent stop.
